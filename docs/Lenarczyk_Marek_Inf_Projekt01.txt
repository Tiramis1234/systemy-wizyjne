==============================================================================
1. STAGE GOAL
==============================================================================

Build the base application that all later stages extend. The interface, the
handling of image sources and the image processing are kept in separate
layers. The application loads JPG/PNG images, plays video files, shows a live
camera preview, displays the input and the result side by side, saves the
result and reports errors without freezing the interface.

==============================================================================
2. ARCHITECTURE AND TECHNOLOGY
==============================================================================

- Backend: Python 3.13 + FastAPI + OpenCV (opencv-python-headless 5.0).
  Python 3.13 is pinned instead of the system 3.14 because OpenCV and NumPy
  wheels for 3.13 are well established.
- Frontend: Vue 3 + Vite. It only calls the HTTP API; no image processing.
- Run: locally (uv run fastapi dev app/main.py, npm run dev) or with
  Docker Compose (backend + frontend services).
- The camera is passed to Docker only through an optional override file
  (compose.camera.yaml), so the default "docker compose up" also works on a
  machine without a camera.

Layers (required separation of interface, sources and processing):

  app/core/     processing: pure functions working on numpy arrays,
                no web or source code
  app/sources/  image sources: image file, video file, camera
                (opening, checking, releasing)
  app/api/      HTTP layer: thin FastAPI routers, no processing logic
  frontend/     user interface

Starter data from the course package was moved to data/samples/
(obraz_testowy.png 640x420 RGB, ruch_testowy.avi 640x360 MJPEG, 15 fps,
195 frames).

3.1 Loading JPG/PNG images and image info  [minimum]
----------------------------------------------------
- An image can be loaded by a path on the server (with suggestions from
  data/samples/) or uploaded from the browser.
- Shown: the image, resolution (width x height), number of channels and data
  type (e.g. 640 x 420 px, 3 channels, uint8 for obraz_testowy.png).
- Methods and parameters:
  * Files are read with cv2.imdecode(..., IMREAD_UNCHANGED). UNCHANGED keeps
    the original number of channels (grayscale = 1, RGBA = 4) and bit depth
    (uint8/uint16), so the info panel shows what really is in the file instead
    of a forced 3-channel 8-bit conversion.
  * Bytes are read first and decoded second instead of using cv2.imread,
    because imread returns None for every problem; this way a missing file
    and a corrupted file produce two different, precise messages.
  * Accepted extensions: .png, .jpg, .jpeg (required formats; .jpeg is the
    same format as .jpg).
- Colors: images stay in OpenCV's BGR order internally. The preview is sent
  to the browser as PNG made by cv2.imencode, which expects BGR and writes a
  standard RGB file - so there is no manual channel swap that could be
  forgotten or done twice. A test checks that the red square of
  obraz_testowy.png is still red (R > 150, B < 100) after loading.
- Errors (HTTP status + message shown in the interface):
  * wrong path            -> 404 "File does not exist: <path>"
  * unsupported extension -> 404 "Unsupported file type ..."
  * corrupted/empty file  -> 400 "The file is not a valid image or is corrupted."
- Tests: 9 unit tests of loading/decoding/encoding on synthetic images and the
  sample image, 3 tests of image info, 7 API tests (TestClient).

3.2 Input and result panels, reset  [minimum; grayscale operation = extra]
--------------------------------------------------------------------------
- Two panels side by side: Input and Result, each with its own image info.
- A new input (file, video frame, camera frame) makes the result a copy of it.
- Operation selector: "none" (copy of input) and "grayscale". P01 requires no
  processing; grayscale is one demonstration operation so that the result
  panel, reset and saving have something visible to work on.
- Grayscale: cv2.cvtColor BGR2GRAY (BGRA2GRAY for images with alpha), i.e.
  Y = 0.299 R + 0.587 G + 0.114 B (ITU-R BT.601). These weights match how
  bright the eye perceives each color; a test checks pure green -> 150 and
  pure blue -> 29. A 1-channel input is returned unchanged.
- The operation is always applied to the input, never to the previous result,
  so repeated clicks do not stack up and the result is always explainable.
- Reset: the result becomes a copy of the input again.
- Errors: applying/resetting without an input -> 404 with message; unknown
  operation -> 422 (validated by the Operation enum).
- Tests: 9 operation tests (incl. "input is never modified" for every
  operation), 4 workspace tests, 5 API tests.

3.3 Saving the result as PNG/JPG  [minimum; browser download = extra]
---------------------------------------------------------------------
- "Save on server": the result is written to a path given by the user
  (default output/result.png). The format follows the extension:
  .png (lossless) or .jpg/.jpeg.
- "Download PNG / JPG": the result is sent to the browser as a file.
- Parameters:
  * JPEG quality = 95 (cv2.IMWRITE_JPEG_QUALITY). This is OpenCV's own
    default: artifacts are not visible on inspection images while the file is
    much smaller than PNG. PNG uses OpenCV defaults (lossless).
- The image is encoded with cv2.imencode and written with Python file I/O
  instead of cv2.imwrite, because imwrite only returns False on failure,
  while an OSError says why (missing permissions, target is a directory).
- Errors (400 + message):
  * directory does not exist -> "Directory does not exist: <dir>"
  * unsupported extension    -> "Unsupported file type ..."
  * permissions / target is a directory -> "Could not save <path>: <reason>"
- Docker: the backend container runs as the host user (user: 1000:1000 by
  default), and output/ exists in the repository. Problem found during
  testing: Docker created a missing bind-mount directory as root, so saving
  later failed with "Permission denied" - both changes fix that.
- Tests: 5 unit tests of saving (PNG round trip, JPG, missing directory,
  bad extension, directory as target), 3 API tests.

3.4 Video playback  [minimum]
-----------------------------
- Open a video file by path (e.g. data/samples/ruch_testowy.avi).
- Play / Pause, a slider to choose any frame, frame counter with fps.
- At the last frame playback stops and the button changes to "Replay",
  which starts again from frame 0.
- "Use frame as input" copies the shown frame into the Input panel, so it can
  be processed, reset and saved like a loaded image.
- Source handling (app/sources/video_source.py, no web code):
  * The file must exist and cv2.VideoCapture.isOpened() must be true; a file
    that opens but reports 0 frames is also rejected (e.g. a text file
    renamed to .avi). Each case has its own message.
  * read_frame(index) checks the range 0..frame_count-1. During normal
    playback frames are requested in order, so the decoder just reads the
    next frame; seeking (CAP_PROP_POS_FRAMES) is used only on a jump
    (slider, replay). For MJPEG every frame is a key frame, so seeking is
    exact.
  * release() and use as a context manager ("with VideoSource(...)") free
    the file handle.
- Timing: the frontend asks for the next frame every 1/fps seconds
  (66.7 ms at 15 fps), minus the time the request took. A frame request takes
  about 4 ms locally (640x360, PNG), so the original speed is kept. The next
  request starts only after the previous one finished, so requests never
  pile up when the backend is slower.
- Changing the source without restart: app/sources/manager.py keeps exactly
  one active video/camera source. Opening another video or loading a still
  image releases the previous source; the active source is also released
  when the application shuts down (FastAPI lifespan).
- Errors: missing / not-a-video file -> 404, frame out of range -> 400
  ("Frame 500 is out of range (video has frames 0-194)."), no open video
  -> 404, read failure -> 503.
- Tests: synthetic MJPEG video generated in the test (10 frames, frame i has
  gray level 20*i, so each frame is recognizable after lossy compression,
  tolerance 3 levels); the sample video is checked against its description
  (195 frames, 15 fps, 640x360). 9 source tests, 4 source-manager tests,
  7 API tests.
